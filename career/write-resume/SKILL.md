# 简历写作

## 目标

把原始经历转化为简洁、可信、能赢得面试机会的简历。把简历当作一份“决策材料”：每个部分都应该帮助读者判断“这个人值得进入面试”。

## 核心原则

- 提供**决策点**：用事实支撑候选人值得继续推进。
- 只在真实且可自证的前提下制造**挑战点**：强表达应该能引出面试问题，并且候选人答得出来。
- 内容组织优先呈现最强证据，不机械复制模板中的示例内容；生成正式文件时，视觉和布局仍必须遵循“模板一致性”要求。
- 用证据替代标签。不要只说“owner 意识强”，要通过范围、决策、取舍和结果展示 ownership。
- 量化有决策价值的结果；没有可靠数字时，可以写清技术取舍、交付范围或团队工作方式的变化，不为了每条都有数字而添加弱指标。
- 数值变化优先写同口径的“从 A 到 B”，并核对统计周期、样本范围和比较对象。只有终值时可客观陈述终值；只有有据可查的变化比例时保留比例及口径，不倒推未知基线。无法支持的变化结论改为已确认事实，关键缺口才追问。百分比与百分点必须区分，例如从 18% 到 24% 是提升 6 个百分点。
- 区分个人贡献、系统规模与业务共同结果。读取双跑不等于双写，协作人数不等于直属团队，迁移零事故不等于整个平台零故障。日常与应急、规则发布与规划发布等指标不合并；不同版本口径不同，不能直接判断哪个结果更好。
- 保持真实。可以优化表达，但不要编造事实、数字、职级或 ownership。资料不足时，使用待确认占位符、提出针对性问题，或说明可补充的证据类型。
- 面向快速浏览写作：bullet 简短，每条只表达一个重点，强信息前置。
- 跨行重要文本块的末行不得只剩少量字词。检查范围至少包括 bullet、项目描述、角色说明、联系方式、目标岗位、项目标题和 Mock 标识；末行必须同时包含至少 8 个有效字符并占该文本块参考行宽至少 15%。固定流水线以 PDF 实际排版坐标强制检查，任一不满足即构建失败。
- 非末页不得因显式分页、整体防拆或不合理的内容编排留下大块底部空白。固定流水线要求非末页最下方可见内容默认达到页面高度的 82%；未达到时先修复分页和内容流，不得靠缩小字体、压缩页边距或降低门禁掩盖问题。
- 让简历 bullet 能匹配面试故事。简历给出论点和关键证据，面试展开细节。

## 工作流程

1. **确定任务与交付形式**
   - 先判断用户需要比较/诊断、整体改写、局部修改、针对 JD 定制，还是生成完整文件。比较或诊断只读原件，先给判断和证据，不自动改写或导出。
   - 比较版本时读取用户指定的实际附件，不用同名旧文件或可编辑稿代替；PDF 同时检查正文和所有相关页面的实际渲染。区分表达质量与事实核验，不凭排版或更大数字判优。
   - 局部修改继承最新已接受稿和偏好，只处理指定内容；不擅自恢复旧章节顺序、迁移术语或指标范围。
   - 用户指定的格式、模板和交付方式优先；修改现有简历时，默认保留原格式和有用的视觉设计。生成新的完整简历文件时，必须执行下方“模板一致性”规则。
   - 用户只需要内容优化时，直接在对话中交付，不额外生成文件。

2. **引导用户提供信息**
   - 生成完整简历或进行大范围重写前，读取 `references/resume-intake.md`，根据其中的采集表引导用户提供目标岗位、原始经历、证据、教育与技能、输出要求和隐私约束。
   - 先从用户已经提供的简历、JD、作品集、经历笔记和对话中提取信息，列出“已掌握的信息”和“仍影响成稿的关键缺口”；不要让用户重复填写已有内容。
   - 用户没有现成简历时，给出可直接复制填写的采集表。明确说明无需润色，可以提供零散事实；不知道、不适用或不愿披露的项目可分别标记为“待补充”“不适用”或“不披露”。
   - 局部诊断或改写只收集完成当前任务所需的信息，不要求用户填写完整采集表。
   - 优先一次性追问会改变岗位定位、内容取舍或强主张可信度的缺口。非关键缺口可以保留待确认占位符，不要以信息不完整为由阻塞可交付的草稿。

3. **明确目标**
   - 明确目标岗位、职级、行业、公司类型，以及简历主要面向真人阅读、ATS 系统，还是两者兼顾。
   - 如果有 JD，提取核心要求和必要关键词。
   - 如果目标未知，基于用户最强证据优化到最合理的目标岗位。

4. **盘点证据**
   - 收集工作经历、教育背景、项目、成果、指标、奖项、论文、开源项目、作品集和有意义的兴趣爱好。
   - 核对数值变化的基线、终值或已证实比例，以及统计周期和样本范围；只追问影响定位或强主张的缺口，其他内容使用已确认事实继续成稿。
   - 区分“项目发生了什么”和“候选人个人负责了什么”。
   - 区分原文记录、用户本轮确认、待核实与未来计划；用户确认可以作为来源，但不等于外部核验。生成或实质改写时，在用户材料目录维护简短来源说明：`最终表述 | 来源/本轮确认 | 范围与待核实项`；只读评价无需新建记录。

5. **找到决策点**
   - 按岗位相关性、稀缺性、可信度、近期程度和可量化影响对证据排序。
   - 把最强类别放在前面：个人概要、工作经历、项目经历、教育背景、作品集或技能。
   - 删除无法提供决策价值的内容。

6. **起草结构**
   - 头部：姓名、联系方式、目标岗位、地点/到岗情况等有用信息。
   - 个人概要：通常 2-3 条，说明岗位定位、代表性成果和可信认可。用一个最有辨识度的结果或规模替换“具备治理和交付经验”等泛泛评价，不照搬整个项目指标清单。
   - 工作经历：公司、岗位与日期，加一句实际负责范围；域负责人、技术接口人或 POC 需说明负责什么，不能只写头衔。
   - 项目：默认使用“标题 + 1-2 行背景/角色/必要规模 + 按贡献主题聚合的要点”。每条连接约束或关键取舍、行动与对应结果，避免机械拆成“问题定义—核心职责—项目结果”后重复同一事实。重点项目通常 3-4 条，必要时可保留 5 条；不把条数当硬限制。
   - 高级研发或 Owner 项目保留可解释的技术选择，并选有证据的要点展示技术能力如何改变发布、接入或协作方式；不把整份简历写成实现清单或管理口号。
   - 技能：只做简洁关键词总结；避免“熟悉/精通/掌握”这类空泛填充。
   - 教育背景：学生或新人放前面；有经验候选人放后面，除非学校本身是强信号。
   - 作品/兴趣：只有当它能证明长期投入、质量、个性或岗位相关能力时才保留。

7. **编写与验证**
   - 用最适合证据的 bullet 结构，常见模式是：`背景/规模 + 行动/决策 + 结果`，不必强行套用。
   - 逐条核对数值比较的单位、口径、时间窗口和对象；未知基线不倒推，不把计划写成成果，也不把业务结果全部归因于单一技术机制。定性贡献需要具体行动和可观察变化，不强造数字。
   - 每条顶部 bullet 都应该回答：“为什么面试官应该关心？”
   - 每个强主张都应该回答：“候选人能否用 3 分钟讲清楚并自证？”
   - 删除空泛形容词、无支撑技能、泛泛职责、不相关个人信息和密集段落。
   - 检查格式是否支持快速浏览：每条 bullet 一个想法，视觉层级清晰，没有意外换行或断页。
   - 出现 bullet、项目描述或其他重要文本块末行孤字时，优先精简、改写或调整语序，让信息自然回流；不得靠全局缩小字号、压缩页边距、按 HTML 预览猜测或降低校验阈值掩盖问题。

8. **生成正式文件**
   - 新建 HTML/PDF 时必须使用下方固定流水线：先从模板生成带指纹的副本，只修改副本，再由脚本构建和自动检查。
   - 不直接编辑 `references/anonymized-growth-product-manager-resume.html`，不手写 Chrome 导出命令，也不接受未经过模板初始化的 HTML 作为正式来源。

## 模板一致性（强制）

- 当用户要求生成完整简历或正式简历文件，且没有明确指定另一种视觉样式时，**必须**先读取 `references/anonymized-growth-product-manager-resume.html`，再开始排版。“按照模板”、“按照要求生成”或类似表达，均视为要求使用该模板。
- 模板是新建文件的默认视觉基线。除非用户明确要求其他样式，保留单栏页面、蓝色主色、浅蓝色整行章节条、左侧蓝色强调线、头部信息层级、公司与日期对齐、项目分块、打印边距和整体字号密度。模板中的长篇项目正文和“问题定义/核心职责/项目结果”小节只用于采集素材，成稿应按贡献主题合并；它们不是必须保留的结构。
- 可以根据候选人证据调整章节顺序、页数和项目数量，但不得改变模板的核心视觉语言，也不得复用模板中的虚构人物、项目或指标作为用户事实。
- 生成 PDF 或 DOCX 时也必须复刻该模板的视觉结构。更换渲染工具或文件格式，不构成改用另一套设计的理由。
- ATS 兼容、快速浏览和页数控制应在模板内实现。不得以 ATS、强制一页、减少留白或个人审美为由，改成极简样式、侧边栏、卡片、时间线或其他未经用户要求的布局。
- 交付前必须渲染成品并与模板做视觉对照，检查上述核心特征是否保留。任何有意偏离都必须由用户的明确要求或无法避免的技术限制支持，并在交付时说明。

## 字体规范（强制）

- 用户未指定其他字体时，新生成完整简历的中文固定使用 **PingFang SC（苹方-简）**，英文、数字和常用拉丁符号固定使用 **SF Pro**；正文使用 Regular，次级强调使用 Medium，标题与关键结果使用 Semibold/Bold。
- HTML/PDF 模板必须使用字体栈：`"ResumePingFang", -apple-system, BlinkMacSystemFont, "SF Pro Text", "SF Pro Display", "ResumeArialUnicode", "Arial Unicode MS", "Microsoft YaHei", Arial, sans-serif`。`ResumePingFang` 由固定流水线从本机 PingFang SC 按当前简历实际字符生成 Regular、Medium、Semibold 三个子集，避免 Chrome 把常用汉字映射为 CJK 部首；不得绕过该子集步骤直接调用系统 PingFang。
- `ResumeArialUnicode` 仅作为缺字和 ATS 文本映射的后备字体保留，不得作为默认视觉字体。PDF 构建仍必须通过 CJK 部首泄漏、可提取文本和必备关键词检查；不得以字体外观正常为由跳过 ATS 校验。
- 交付前除逐页视觉检查外，还要检查 PDF 字体资源：中文应出现 `PingFangSC`，英文与数字应出现 `.SFNS` 或 `SF Pro`。若运行环境缺少这些字体或 Chrome 无法安全导出，必须说明技术限制，不得静默替换默认字体。
- 修改用户已有简历时默认保留原字体；只有用户要求套用本 skill 的默认样式时，才改为上述字体规范。

## 文件格式

- 用户指定格式时必须遵循；修改现有文件时默认原格式交付。
- 未指定但确实需要文件时，按用途选择：可协作编辑优先 DOCX，固定版式投递优先 PDF，用户需要可持续维护的网页源文件时使用 HTML。只在格式选择会明显改变交付结果时追问。
- 交付 PDF 或 DOCX 前渲染并检查分页、换行、边距、字体、链接和联系方式的可读性。
- 生成 HTML 时使用语义化结构和可打印 CSS。HTML 转 PDF 必须使用固定流水线脚本；脚本同时传入兼容的新旧页眉页脚关闭参数，并验证 PDF 中不存在文件 URL 或额外页眉。

## HTML/PDF 固定流水线（强制）

脚本位置为当前 skill 目录下的 `scripts/resume_pipeline.py`。所有路径使用绝对路径。

1. 当前会话第一次生成 PDF 前，先按 PDF skill 的要求登记一次 artifact 创建操作；不要在重建时重复登记。
2. 运行一次环境检查；`doctor` 必须确认本机 PingFang SC、FontTools、Chrome、Poppler 和 PDF 依赖可用：

   ```bash
   /absolute/path/to/write-resume/scripts/resume_pipeline.py doctor
   ```

   如果只缺少 FontTools，使用当前流水线的 Python 环境安装 skill 自带依赖：

   ```bash
   python3 -m pip install -r /absolute/path/to/write-resume/scripts/requirements.txt
   ```

3. 在当前任务的 `work/` 下初始化新的 HTML 副本：

   ```bash
   /absolute/path/to/write-resume/scripts/resume_pipeline.py init \
     --output /absolute/path/to/work/resume-source.html
   ```

   `init` 会复制当前标准模板并写入模板指纹。目标文件已存在时会停止，避免覆盖用户编辑。

4. 只用 `apply_patch` 修改 `resume-source.html`。保留文件顶部的 `resume-pipeline` 指纹注释以及模板的核心 CSS、打印规则、`ResumePingFang` 和 ATS 后备字体声明。`build` 会在本轮 QA 目录生成渲染副本及仅供本次构建使用的 `resume-fonts/` 字体子集；不得手工复制或交付系统字体文件。
5. 由脚本构建 PDF，并把 QA 产物写入 `work/`：

   ```bash
   /absolute/path/to/write-resume/scripts/resume_pipeline.py build \
     --html /absolute/path/to/work/resume-source.html \
     --pdf /absolute/path/to/outputs/resume.pdf \
     --qa-dir /absolute/path/to/work/resume-qa \
     --expected-pages 2 \
     --required-term 目标岗位关键词
   ```

   对每个必须被 ATS 命中的核心 JD 词重复传入 `--required-term`。有用户特定的旧姓名、旧公司或占位内容时，重复传入 `--forbid-term`。只有明确重建同一 PDF 时使用 `--overwrite`。
   非末页填充率默认门禁为 82%。只有版式明确要求有意留白、逐页视觉复核确认合理且向用户说明原因时，才允许显式传入更低的 `--min-nonfinal-fill`；不得为让构建通过而调低或关闭门禁。
6. 如果 Chrome 返回成功但没有 PDF，按脚本提示对**同一条 build 命令**申请 GUI/沙箱权限后重试；不要绕开脚本直接调用 Chrome。
7. 构建成功只代表自动检查通过。必须查看 QA 目录中的每页 PNG 或 `contact-sheet.png`，与标准模板做视觉对照，确认无截断、重叠、异常拆页、非末页大块底部空白、任何文本块末行孤字、浏览器页眉页脚、字体过小或联系方式不可读；发现问题后修改 HTML 副本并重新 `build --overwrite`。

脚本自动检查：模板指纹与版本、模板示例残留、核心结构、A4 与页数、章节标题必须先于章节正文、必备关键词、空白/图片化页面、非末页最下方可见内容默认达到页面高度 82%、跨行重要文本块末行至少 8 个有效字符且至少占该文本块参考行宽 15%、浏览器文件 URL、CJK 部首编码泄漏、真实 PDF 字体和逐页 PNG 数量；最终 PDF 通过临时文件验证后再原子替换，失败不会破坏上一版。非末页填充率与末行孤字校验都以 PDF 实际渲染结果为准，不得用 HTML 预览或固定字数替代。

## 输出风格

撰写或改写时，直接给出优化后的简历内容；需要生成文件时，按“文件格式”中的用户意图和使用场景选择交付形式。比较时，先推荐投递主版本并说明适用岗位，再用具体条目解释优势、旧版值得保留之处和少量优先修改项；没有 JD 时说明判断所采用的岗位方向。诊断时，先给最高影响的建议，再给必要的改写示例。不默认打主观分数，不把文案可信度判断写成事实已核实。除非用户主动要求教学，否则避免泛泛的简历建议。

语言优先级为：用户明确指定的投递语言 > 目标 JD 的语言 > 原简历的语言。保留用户所在行业的表达风格，除非目标岗位需要另一种语气。

## 参考

- 生成完整简历、大范围重写，或用户不知道该提供哪些材料时，读取 `references/resume-intake.md`，使用其中的采集策略和可复制模板；局部改写时只选取与当前任务有关的字段。
- 完整撰写、bullet 改写、量化证据补充或整份诊断时，读取 `references/resume-patterns.md`，使用其公式、案例和评分标准。
- 生成任何新的完整简历文件时，按“模板一致性”的强制要求读取 `references/anonymized-growth-product-manager-resume.html`。对非产品岗位，保留视觉和布局体系，根据岗位证据调整内容结构。该文件中的人物、项目和数据均为虚构示例，不得复用为用户事实。
- 生成或排查 HTML/PDF 时读取 `references/html-pdf-workflow.md`，了解固定流水线的非显然约束、故障含义和人工视觉检查边界。
