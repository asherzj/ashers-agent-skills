# 疑难 Bug 交付流程

先完整运行 `diagnosing-bugs`，再使用 `implement` 完成交付收尾。开始前读取仓库配置、相关领域术语、ADR 和原始 Issue。

## 范围门禁

先确认用户要求的终点。只要求诊断并不授权修改代码、提交、推送或关闭 Issue；只有用户明确要求修复或交付时才运行完整流程。

## 流程

1. 调用 `diagnosing-bugs`。在提出理论或修复前，必须先得到一条紧密、可变红、已经实际运行过的反馈命令；随后按其要求完成复现、最小化、排序假设、定向插桩、回归测试、修复和清理。所有展示的命令与产物必须先脱敏。
2. 如果无法建立紧密反馈回路，列出尝试过的办法和缺少的产物或权限，然后停止。禁止在没有反馈回路时猜测原因。
3. 如果不存在正确的回归测试接缝，记录这个架构发现，不要添加虚假的浅层测试。可把 `improve-codebase-architecture` 作为后续工作，但不要悄悄把 Bug 修复扩大成重构。
4. 诊断已经得到验证过的修复并完成清理后，调用 `implement` 作为交付外壳。不要重新诊断或重写修复；只用它核对验收条件、运行聚焦与完整检查、调用 `code-review`、创建工单级提交、推送，并在获授权时关闭事项。

只要求诊断时，在给出证据支持的根因和修复建议后停止，并保存反馈命令供后续修复会话复用。

## 完成条件

汇报反馈命令、根因、回归覆盖或缺失接缝、原始场景验证、插桩清理、评审结果、提交、远端分支和最终 Issue 状态。仅在本地修好但没有推送，不算交付。
