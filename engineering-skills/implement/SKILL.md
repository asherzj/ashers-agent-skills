# 实现并交付一张工单

实现用户在一份 spec（规格说明）或一张工单中描述的工作。一张工单是一次实现、验证、评审、提交和推送的最小交付单元；不要把多张工单揉进同一个提交。

用户显式调用本 Skill，或明确要求“交付”“提交并推送”，可视为提交与推送授权；模型自动选择的上层流程不能替代用户授权。这项授权不自动包含合并 PR、强制推送、改写远端历史或关闭工单；这些动作仍受用户要求和工单系统规则约束。

## 开始前

1. 读取仓库的 `AGENTS.md`，以及已配置的工单系统、领域文档和相关 ADR。
2. 完整读取 spec 或工单的正文与评论，提取验收标准、范围外事项和交付证据。信息不足以安全实现时，先补齐缺口，不要自行发明需求。
3. 检查当前分支、默认分支、远端和工作树状态。保留所有既有及无关改动；如果存在无法归属的修改，先停下并报告。
4. 如果当前位于默认分支，先创建工单级分支再编辑。除非用户明确要求，否则禁止直接提交或推送到默认分支。

如果并行实现多张工单，每张工单必须使用独立分支和隔离的 git worktree；多个 agent 不得共享可写 checkout。无法隔离时改为顺序执行，完成一张工单的提交与推送周期后再开始下一张。

## 实现与验证

- 在适用且已约定的测试接缝处，加载并完整遵循 `tdd` Skill；不要写死特定客户端的 slash command。
- 实现过程中反复运行最相关的单个测试和类型检查。结束时运行一次完整测试套件和仓库要求的其他验证。任何必需检查无法运行时，按阻塞处理；只有用户或仓库规则明确允许替代验证时，才执行当前最强的可用替代并说明差异。
- 满足验收标准后，以本工单分支的固定基点和原始 spec/工单为输入，加载并完整遵循 `code-review` Skill。修复阻塞性交付的问题并重新验证。

## 完成工单

只有在验收标准、必要测试和评审都通过后，才能进入本阶段。任何必需检查仍失败或受阻时，不得提交、推送或关闭工单；应报告准确的阻塞原因。

1. 检查分支、工作树状态和完整 diff。只暂存属于本工单的文件与删除项；在脏工作树中禁止使用 `git add .`、`git add -A` 或 `git add --all`。
2. 创建一个带工单引用的简洁提交。提交后核对其完整内容，确认没有无关路径。
3. 使用 `git push -u origin HEAD` 推送当前工单分支。已按上文取得用户对提交与推送的授权时，无需再次进行对话确认，但工具或平台审批仍可能需要。除非用户明确要求，否则绝不强制推送。
4. 如果推送被拒绝，立即停止。不得自动 rebase、merge、覆盖远端工作或关闭工单；报告本地 commit SHA 和拒绝原因。
5. 推送成功后，验证远端分支和本地工作树。只有工单系统工作流授权实现 agent 收尾时，才发布完成证据并关闭工单。

最终汇报交付行为、验收标准、验证与评审结果、commit SHA、远端分支和工单最终状态。提交只存在于本地时，不得声称已经交付。
