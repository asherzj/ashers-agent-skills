# UI 原型

在单一路由上生成**多个截然不同的 UI 变体**，可从一个悬浮底栏切换。用户在浏览器里翻看各变体，选定一个（或从各处偷些片段），然后把其余的扔掉。

如果问题关乎逻辑/状态而非外观，那就走错了分支。请使用 [LOGIC.md](LOGIC.md)。

## 何时适合用这种形态

- 「这个页面应该长什么样？」
- 「我想在拍板前先看看这个仪表盘的几个方案。」
- 「给设置屏换一种布局试试。」
- 任何用户原本要在脑子里三个模糊草稿之间纠结一整天的情况。

## 两种子形态：强烈偏好子形态 A

当 UI 原型**与应用的其余部分贴着放**时，评判起来要容易得多：真实的顶栏、真实的侧边栏、真实的数据、真实的密度。孤立的一次性路由是一个真空：每个变体单独看都不错。只要存在一个合理的现有页面可以承载变体，就默认选子形态 A。只有当原型确实没有近旁的安身之处时，才动用子形态 B。

### 子形态 A：对现有页面的调整（首选）

路由已存在。变体渲染在**同一路由**上，由 `?variant=` 这个 URL 查询参数门控。现有的数据获取、参数和鉴权全部保留，只换渲染。这是默认选项；除非有明确理由不选，否则就选它。

如果原型针对的东西还没有页面，但*天然属于某个页面之内*（仪表盘的一个新区块、设置屏的一张新卡片、现有流程中的一个新步骤），那它仍属子形态 A。把变体挂载到宿主页面里。

### 子形态 B：新页面（最后手段）

只有当被做原型的东西确实没有可以栖身的现有页面时才用它（例如一个全新的顶层界面，或一段无法嵌入任何合理位置的流程）。

按项目已有的路由约定创建一条**一次性路由**。不要发明新的顶层结构。给它起一个一眼可见是原型的名字（例如在路径或文件名中包含 `prototype` 一词）。沿用同样的 `?variant=` 模式。

在确定采用子形态 B 之前，先自查：真的没有任何现有页面可以嵌入吗？空路由会藏住有内容路由本会暴露的设计问题。

两种子形态下的悬浮底栏完全相同。

## 流程

### 1. 陈述问题并选定 N

默认**3 个变体**。超过 5 个就不再是截然不同，而开始变成噪声，所以封顶于此。

把方案写成一行，放在原型所在位置或文件顶部注释中：

> 「设置页面的三个变体，通过 `?variant=` 切换，位于现有的 `/settings` 路由上。」

无论用户当下是否会来挑刺，这样写都管用。

### 2. 生成截然不同的变体

起草每个变体。每个变体都要满足：

- 页面的用途及其可访问的数据。
- 项目的组件库/样式系统（TailwindCSS、shadcn、MUI、纯 CSS，无论哪种）。
- 一个清晰的导出组件名，例如 `VariantA`、`VariantB`、`VariantC`。

变体必须在**结构上不同**：不同的布局、不同的信息层级、不同的主要操作入口（affordance），而不只是颜色不同。三个略作调整的卡片网格不是 UI 原型，是墙纸。如果两个草稿出来太相似，就带着明确的「不要用卡片网格」指示重做一个。

### 3. 把它们接起来

在路由上创建一个单一的切换器组件：

```tsx
// 伪代码，按项目框架自行适配
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);
```

子形态 A（现有页面）：把所有现有数据获取留在切换器之上；每个变体只改变被渲染的子树。

子形态 B（新页面）：`/prototype/<name>` 下的一次性路由挂载同一个切换器。

### 4. 构建悬浮切换器

屏幕底部中央一个固定定位的小栏，包含三个部分：

- **左箭头**：循环切到上一个变体（可回绕）。
- **变体标签**：显示当前变体键，如果该变体导出了名称，也一并显示。例如 `B (Sidebar layout)`。
- **右箭头**：向前循环切换（可回绕）。

行为：

- 点击箭头会更新 URL 查询参数（使用框架的路由器，例如 Next 的 `router.replace`、React Router 的 `navigate` 等），使变体可分享、刷新后稳定。
- 键盘：`←` 和 `→` 方向键也可循环切换。当 `<input>`、`<textarea>` 或 `[contenteditable]` 聚焦时，不要拦截方向键。
- 视觉上与页面明显区分（例如高对比度的胶囊形、轻微阴影），让人一眼看出它不属于被评估的设计。
- 在生产构建中隐藏：以 `process.env.NODE_ENV !== 'production'` 或等效检查作为门控，以免一次走漏的原型合并把底栏发布给用户。

把切换器放进一个单独的共享组件，让两种子形态都能复用。放在项目存放共享 UI 的地方。

### 5. 交付

把 URL（以及 `?variant=` 的各键）亮出来。用户有空时自然会翻看。有趣的反馈通常是**「我想要 B 的顶栏配 C 的侧边栏」**——那才是他们真正想要的设计。

### 6. 记录答案并清理

一旦某个变体胜出，记录答案（哪个变体、为什么），然后按 [SKILL](SKILL.md) 描述的方式记录原型。把胜者折入真实代码，其余的挪到一次性分支上，而不是留在 main 上：

- **子形态 A**：把胜者折入现有页面；从 main 上删掉落败变体和切换器。
- **子形态 B**：把获胜变体提升为真实路由；从 main 上删掉一次性路由和切换器。

全套变体是一手来源，所以它落到一次性分支上，而不是垃圾桶里，因为留在 main 分支的变体组件和切换器会很快腐烂、迷惑下一位读者。

## 反模式

- **只在颜色或文案上有差异的变体。**那是微调，不是原型。真正的变体在结构上各执己见。
- **变体之间共享过多代码。**共享一个 `<Header>` 没问题；共享一个 `<Layout>` 就背离了初衷。每个变体都应能自由抛弃既有布局。
- **把变体接到真实变更操作上。**只读原型没问题。如果某个变体需要写入，就把它指向一个桩（stub）：问题是「它应该长什么样」，而不是「后端能不能用」。
- **把原型直接提升为生产代码。**变体代码是在原型约束下写的（无测试、极简错误处理）。折入时请正规重写。
