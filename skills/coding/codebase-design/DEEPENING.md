# 深化（Deepening）

在给定依赖的前提下，如何安全地深化一组浅模块。假定你已掌握 [SKILL.md](SKILL.md) 中的词汇：**模块（module）**、**接口（interface）**、**接缝（seam）**、**适配器（adapter）**。

## 依赖类别

评估某个深化候选时，先为它的依赖分类。类别决定了深化后的模块如何跨接缝测试。

### 1. 进程内（In-process）

纯计算、内存状态、无 I/O。永远可以深化：合并这些模块，直接通过新接口测试。不需要适配器。

### 2. 本地可替换（Local-substitutable）

拥有本地测试替身的依赖（用 PGLite 顶替 Postgres、内存文件系统）。只要替身存在就可以深化。深化后的模块在测试套件中以运行替身的方式测试。接缝是内部的；模块的外部接口上没有端口。

### 3. 远程但自有（Ports & Adapters）

跨网络边界的自有服务（微服务、内部 API）。在接缝处定义一个**端口（port）**（接口）。深模块拥有逻辑；传输层作为**适配器**注入。测试使用内存适配器。生产使用 HTTP/gRPC/队列适配器。

推荐的表述：*"在接缝处定义一个端口，为生产实现 HTTP 适配器、为测试实现内存适配器，这样即便跨网络部署，逻辑也坐落在一个深模块里。"*

### 4. 真正的外部（Mock）

你不掌控的第三方服务（Stripe、Twilio 等）。深化后的模块把外部依赖当作注入的端口；测试提供一个 mock 适配器。

## 接缝纪律

- **一个适配器意味着假想接缝。两个适配器才意味着真接缝。** 除非至少能成立两个适配器（通常是生产 + 测试），否则不要引入端口。单适配器的接缝只是一层间接。
- **内部接缝 vs 外部接缝。** 深模块除了接口处的外部接缝，还可以有内部接缝（私有于其实现，供它自己的测试使用）。不要仅仅因为测试会用到内部接缝，就把它们通过接口暴露出去。

## 测试策略：替换，而不是叠加

- 浅模块上的旧单元测试，在深化模块的接口处有了测试之后就成了废物；删掉它们。
- 在深化模块的接口处编写新测试。**接口就是测试面**。
- 测试断言的是通过接口可观察到的结果，而不是内部状态。
- 测试应当能在内部重构后存活，因为它们描述的是行为而非实现。如果实现一变测试就得跟着变，说明它测到了接口以外。
