# 设计两遍（Design It Twice）

当用户想为选定的深化候选探索备选接口时，使用这个并行子代理模式。基于 Ousterhout 的 "Design It Twice"（设计两遍）原则：你的第一个想法不太可能是最好的。

使用 [SKILL.md](SKILL.md) 中的词汇：**模块（module）**、**接口（interface）**、**接缝（seam）**、**适配器（adapter）**、**杠杆（leverage）**。

## 流程

### 1. 框定问题空间

在启动子代理之前，为选定的候选写一段面向用户的问题空间说明：

- 任何新接口都需要满足的约束
- 它将依赖的依赖项，以及各自属于哪个类别（见 [DEEPENING.md](DEEPENING.md)）
- 一段粗略的示意性代码草图，用于落实约束——不是提案，只是让约束具体化的手段

把它展示给用户，然后立即进入第 2 步。用户在子代理并行工作的同时阅读和思考。

### 2. 启动子代理

并行启动 3 个以上的子代理。每个子代理必须为深化后的模块产出一个**截然不同**的接口。

给每个子代理一份独立的技术简报（文件路径、耦合细节、来自 [DEEPENING.md](DEEPENING.md) 的依赖类别、接缝背后是什么）。简报独立于第 1 步面向用户的问题空间说明。给每个代理一个不同的设计约束：

- 代理 1："最小化接口：入口点最多 1–3 个。最大化每个入口点的杠杆。"
- 代理 2："最大化灵活性：支持众多用例与扩展。"
- 代理 3："为最常见的调用方优化：让默认场景毫不费力。"
- 代理 4（如适用）："围绕 ports & adapters 为跨接缝依赖做设计。"

简报中同时纳入 [SKILL.md](SKILL.md) 的词汇和 CONTEXT.md 的词汇，让每个子代理的命名既与架构语言一致，也与项目的领域语言一致。

每个子代理输出：

1. 接口（类型、方法、参数，加上不变量、顺序约束、错误模式）
2. 展示调用方如何使用它的用法示例
3. 实现在接缝背后藏起了什么
4. 依赖策略和适配器（见 [DEEPENING.md](DEEPENING.md)）
5. 权衡：哪里杠杆高，哪里单薄

### 3. 呈现与比较

依次呈现各设计方案，让用户逐一消化，再用文字进行比较。按**深度（depth）**（接口处的杠杆）、**局部性（locality）**（变化集中之处）与**接缝位置**来对比。

比较之后，给出你自己的推荐：你认为哪个设计最强，为什么。如果不同设计的元素能很好地组合，就提出一个混合方案。要有鲜明立场：用户要的是一个明确的判断，不是一份菜单。
