# Ask Matt

你记不住每一个 skill，所以开口问。

**流程（flow）**是穿越这些 skill 的一条路径。大多数路径沿着一条**主流程（main flow）**延伸，另有两个**入口（on-ramp）**汇入其中。其余的一切要么独立成篇，要么是运行在底下的一层词汇。

## 主流程：想法 → 交付

大多数工作走的路线。你有一个想法，想把它做出来。

1. **`/grill-with-docs`** 通过访谈打磨这个想法。每当你**在某个工作目录中干活**，就从这里开始：它是有状态的，会把学到的东西留在 `CONTEXT.md` 和 ADR（架构决策记录）里。（没有工作目录？改用 `/grill-me`，在"独立"一节中有介绍。两者运行的是同一个 `/grilling` 原语；`grill-with-docs` 会留下书面痕迹，所以只要存在一个可以留痕的仓库，它就是两者中更好的那个。）
2. **分支：每个问题都能在对话里敲定吗？** 如果某个问题需要一个可运行的答案（状态、业务逻辑、一个必须亲眼看到的 UI），就绕道原型（prototype），来回两程都由 **`/handoff`** 架桥（原型住在自己的目录里，而这正是 `/handoff` 的用途；见"阶段边界"）：
   - 用 **`/handoff`** 导出，然后基于那个文件开启一个全新会话，
   - 用 **`/prototype`** 以一次性代码回答这个问题，
   - 把你学到的东西用 **`/handoff`** 带回来，并在最初的想法线程里引用它。
3. **分支：这是一次跨多个会话的构建吗？**
   - **是** → **`/to-spec`**（把这段线程整理成 spec（规格说明）），再用 **`/to-tickets`** 把它拆成一张张曳光弹（tracer-bullet）工单，每张工单声明自己的**阻塞边（blocking edges）**。在本地工单系统（issue tracker）上，就是 `.scratch/<feature>/issues/` 下每张工单一个文件，由人按阻塞优先的顺序手工推进；在真实工单系统上，这些边会变成原生的阻塞链接，于是任何阻塞项都已完成的工单都可以直接认领：对每张工单发起 **`/implement`**，**每张之间 `/clear` 清空上下文**。每张工单都是自包含的，所以最后一张的上下文用完即可丢弃。
   - **否** → 就在这里，在同一个上下文窗口中直接 **`/implement`**。

   无论哪条路，**`/implement`** 都会在内部驱动 **`/tdd`** 来构建每个 issue（一次一个红-绿切片），收尾时先运行 **`/code-review`**——一次针对 diff 的双轴评审（标准 + Spec）——再提交。当你只想以测试先行的方式构建某个具体行为、还不需要完整 spec 时，可单独使用 **`/tdd`**；每当你想相对某个固定基准评审一个分支或 PR 时，可单独使用 **`/code-review`**。

### 上下文卫生

把第 1–3 步保持在**同一个不间断的上下文窗口**里（在 `/to-tickets` 完成之前不要 compact 或 clear），这样拷问（grilling）、spec 和工单都建立在同一段思考之上。之后的每个 `/implement` 都全新开始，依据工单干活。

这条路线的上限是 **[smart zone](https://www.aihero.dev/ai-coding-dictionary/smart-zone)**：模型仍能敏锐推理的那个窗口（在最先进的模型上约 15 万 token）。如果某个会话在 `/to-tickets` 之前就逼近了这个上限，不要在降级状态里硬撑；在最近的阶段边界上 `/compact`，然后继续（见"阶段边界"）。

## 入口

一类会生成工作的起始处境，随后汇入主流程。

- **Bug 和请求堆积如山** → **`/triage`**。它带着 issue 走过各个分诊（triage）角色，产出代理可直接上手的 issue，之后由 **`/implement`** 接手。

  分诊只针对**不是你创建的** issue：bug 报告、外部功能请求、任何以原始状态抵达的东西。`/to-tickets` 产出的工单已经是代理就绪的，所以**不要对它们分诊**。

- **有什么东西坏了** → **`/diagnosing-bugs`**。留给难啃的那些：第一眼看不穿的 bug、间歇发作的 flake、在两个已知良好状态之间悄悄溜进来的回归。在拿到**紧密的反馈回路（feedback loop）**（一条已经在这个 bug 上变红的命令）之前，它拒绝提出理论，随后用一个回归测试完成修复。当真正的发现是"没有一个合适的接缝（seam）把这个 bug 锁死"时，它的事后复盘会移交给 **`/improve-codebase-architecture`**。

- **庞大而迷雾重重的工程：绿地项目或超大功能构建，大到一个会话装不下** → **`/wayfinder`**，这里认知要求最高的流程。当从这里到目的地（destination）的路径尚不可见时，它会在工单系统上绘制一张由**决策工单（decision ticket）**组成的**共享地图（shared map）**，并一次解决一个，产出的是**决策而非交付物**，直到迷雾被推开、道路清晰为止。`/grill-with-docs` 打磨的是一个会话装得下的想法，而 wayfinder 面对的是装不下的那种；它更慢也更稠密，所以只留给恰好这种情况，绝不要用在范围已经明确的功能上。

  当地图拨云见日，**它做的是移交，而不是构建**：在 **`/to-spec`** 处汇入主流程，把地图上互相关联的决策收敛成一份可构建的计划，然后照常 `/to-tickets`、`/implement`。把地图直接塞进 `/implement` 会跳过这个收敛步骤、丢掉关联的细节，所以只有当这项工作最终确实很小时，才直接 `/implement`。

## 代码库健康

不是功能开发，只是养护。

- **`/improve-codebase-architecture`** 只要有空闲就可以跑，让代码库保持适合代理作业的状态。它会浮现**深化机会**；选中其中一个就_生成了一个想法_，可以带进主流程的 `/grill-with-docs`。它是找出候选者的勘测；**`/codebase-design`**（见下文）则是设计选中项的工作台。

## 底层词汇

两个由模型调用的参考，运行在其他 skill _之下_，各自是自己那套词汇的唯一事实来源。当问题出在**措辞**而不是流程上时，直接找它们；也可以让上面的 skill 把它们引进来。

- **`/domain-modeling`**：磨利项目的_领域_语言：挑战一个含糊的术语，化解一个过载的词（"account" 一词身兼三职），把一个难以回退的决策记录为 ADR。它是 `/grill-with-docs` 所驱动的主动纪律，让 `CONTEXT.md` 保持一份干净的词汇表。
- **`/codebase-design`** 是深模块（deep module）那套词汇（模块、接口（interface）、深度（depth）、接缝（seam）、适配器（adapter）、杠杆（leverage）、局部性（locality）），用于设计一个模块的_形状_：在一条干净的接缝处，用一个小接口罩住大量行为。`/tdd` 和 `/improve-codebase-architecture` 都讲这套语言。

## 阶段边界

**阶段（phase）**是会话内的一块工作：拷问、实现、QA。在两个阶段之间的**边界**上你有五个选项，而在它们之间挑选，是这整张地图里最模糊的决定：

- **继续**：原地不动。不花成本，不丢东西。
- **`/clear`**：清空窗口，当这里的内容对下一步无关紧要时。
- **`/handoff`** 写出一个可携带的 markdown 文件。适用面窄：仅用于**新 harness**、**新目录**、**同事**，或在阶段_中途_分出一个支线任务。它买到的是可携带性。
- **子代理**：把一个范围收得很紧的任务送进它自己的窗口，换回一份报告。
- **`/compact`** 压缩当前上下文，并用它播种一个新会话。是**默认项**，位于树的底部，而非第一选择。

阅读 [PHASE-BOUNDARIES.md](PHASE-BOUNDARIES.md) 了解那棵按序排列的决策树：五个问题、每个分支背后的推理，以及为什么一手来源的代价使**继续**成为第一个要尝试排除的选项。就在边界**处**做决定；阶段中途，要么继续，要么把剩余工作拆给子代理。

## 独立

完全不在主流程上。

- **`/grill-me`**：与 `/grill-with-docs` 同样不留情面的访谈，但**无状态**：不在本地保存任何东西，也不构建 `CONTEXT.md`。当你**不在工作目录中干活**时用它（打磨一个计划、一个设计、一篇文章，任何底下没有仓库的东西）。如果你在工作目录里，改用 `/grill-with-docs`：它跑同样的访谈并留下书面痕迹，所以严格来说是更好的那个。
- **`/grilling`** 是访谈原语本身：一轮轮提问、前沿（frontier）、找事实是代理的活、做决策是你的活。`/grill-me` 和 `/grill-with-docs` 是两个具名的入口，而 `/triage`、`/wayfinder` 和 `/improve-codebase-architecture` 都在内部运行它。只有当你想要一场不包任何外壳的访谈时，才直接用它。
- **`/resolving-merge-conflicts`** 逐个差异块（hunk）地处理进行中的 merge 或 rebase 冲突，依据追溯到每一侧一手来源的**意图**来裁决，而不是挑行，然后完成整个操作。它从不运行 `--abort`。独立于所有流程之外：当你已经身处冲突之中时用它。
- **`/prototype`** 是一个一次性小程序，回答一个设计问题：这个状态模型对不对味，或者这个 UI 该长什么样。一次性是对代码写法的约束，不是销毁它的承诺：答案会折进真正的代码，而原型本身作为**一手来源**保存在主干之外的一个 `prototype/<name>` 分支上，由实现 issue 指向它。它是主流程第 2 步里的那条岔路，但任何时候只要一个设计问题在纸面上难以敲定，都可以用它。
- **`/research`**：把阅读类的跑腿活交给**后台代理**：它针对**一手来源**调查一个问题，然后在仓库里留下一份带引用的 Markdown 文件。它读书的时候你继续干活。它产出的文件正是要_带进_主流程 `/grill-with-docs` 的东西，因为研究是给思考喂料，而不是取代思考。
- **`/to-questionnaire`** 用在你被卡住的原因既不在你脑子里、也不在代码库里，而在**别人**那里的时候，它会替你给对方写一份问卷。它是 `/grill-me` 的反面：不是就主题访谈你，而是就**发送**这件事访谈你（发给谁、需要收回什么），并把问题对准缺口。收回来的东西是 `/grill-with-docs` 或 `/to-spec` 的原料。
- **`/wizard`** 面向只有**人类**才能执行的步骤：开通基础设施、配置凭据或 CI 密钥、在一个陌生的第三方后台里一路点过去、执行一次性的迁移或切换。它生成一个交互式 bash 脚本，逐个打开 URL、捕获每个值，并写进 `.env` 和 GitHub secrets，让这套流程不再是你每次都要向代理重新解释一遍的东西。由模型自动调用，所以代理一撞上只有你能过的墙，就会立刻伸手用它。代理自己能做的事就该它自己做；这个 skill 属于人类真正在环的环节。
- **`/wait-what`** 是对一条没接住的消息的纠偏。在对话中途、任何其他 skill 的内部都可以用，代理会带着你此前缺失的上下文、用大白话把它刚才说的话重新讲一遍，并使用 `CONTEXT.md` 的词汇。它是事后补救；`/grill-with-docs` 是事前预防，因为趁早达成的一门共享语言，能让行话根本没机会冒头。
- **`/teach`**：跨多个会话学习一个概念，把当前目录用作有状态的工作区。
- **`/writing-for-agents`** 是编写供代理消费的文档的参考：skill、AGENTS.md、被指向的文档。

## 前置条件
