# ADR 格式

ADR 存放在 `docs/adr/` 中，并使用顺序编号：`0001-slug.md`、`0002-slug.md` 等。

惰性创建 `docs/adr/` 目录：只在需要第一个 ADR 时才创建。

## 模板

```md
# {Short title of the decision}

{1-3 sentences: what's the context, what did we decide, and why.}
```

就这样。一个 ADR 可以只有一段话。价值在于记录*做出了某个决定*以及*为什么*，而不在于填满各个小节。

## 可选小节

只在它们能带来真正价值时才包含。大多数 ADR 用不到。

- **Status** frontmatter（`proposed | accepted | deprecated | superseded by ADR-NNNN`）：当决策会被重新审视时有用
- **Considered Options**：只在被否决的备选方案值得记住时使用
- **Consequences**：只在需要点出不明显的下游影响时使用

## 编号

扫描 `docs/adr/`，找到现有的最大编号并加一。

## 何时提议 ADR

以下三条必须全部成立：

1. **难以逆转**：之后再改变主意的代价是实质性的
2. **脱离上下文令人意外**：未来的读者看到代码会问"他们到底为什么这么做？"
3. **一次真实权衡的结果**：存在真正的备选方案，而你出于具体理由选了其中一个

如果决策容易逆转，跳过它：到时候直接逆转就是。如果它不令人意外，没人会问为什么。如果没有真正的备选方案，除了「我们做了显然的事」之外没什么可记录的。

### 符合条件的情况

- **架构形态。** "我们在用 monorepo。""写模型采用事件溯源，读模型投影到 Postgres。"
- **上下文之间的集成模式。** "Ordering 和 Billing 通过领域事件通信，而不是同步 HTTP。"
- **带有锁定效应的技术选型。** 数据库、消息总线、认证提供方、部署目标。不是每个库都算：只是那些换掉要花一个季度的。
- **边界与范围决策。** "客户数据归 Customer 上下文所有；其他上下文仅通过 ID 引用它。"明确的「不」与「是」同样有价值。
- **对显然路径的刻意偏离。** "我们因为 X 而用手写 SQL 而不是 ORM。"任何合理读者会假设相反做法的情形。这些记录能阻止下一位工程师去"修复"本是刻意为之的东西。
- **代码中看不到的约束。** "由于合规要求，我们不能用 AWS。""响应时间必须低于 200ms，因为合作方 API 合同。"
- **否决理由不明显的备选方案。** 如果你考虑过 GraphQL 却因微妙的原因选了 REST，把它记下来；否则六个月后有人会再次提议 GraphQL。
