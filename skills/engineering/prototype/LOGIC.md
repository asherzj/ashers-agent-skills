# 逻辑原型

一个单一、自包含的 HTML 文件（一份**可分享的演示**），让任何人都能通过点击按钮驱动一个状态模型。当问题涉及**业务逻辑、状态转换或数据形状**时使用它：这类东西在纸面上看着合理，只有推进到真实案例时才觉得不对劲。

因为它是单个文件、无需安装任何东西，你可以把它交给非开发者（设计师、产品经理、领域专家），让他们亲自感受这个模型。所以它要说他们的语言，而不是代码的语言。

## 何时适合用这种形态

- 「我不确定这个状态机能否处理 X 之后 Y 的边界情况。」
- 「这个数据模型真的能让我表达……的情况吗？」
- 「我想在动手写之前，先摸清楚这个 API 应该长什么样。」
- 任何有人想**按按钮、看状态变化**的场景。

如果问题是「它应该长什么样」，那就走错了分支。请使用 [UI.md](UI.md)。

## 流程

### 1. 陈述问题

在写代码之前，先写下你在做原型的是哪个状态模型、哪个问题。一段话，放在演示的顶部（以可见的简介形式，而不只是一条注释）。回答错误问题的逻辑原型纯属浪费，所以要把问题写明白，以便日后核对——无论用户此刻在场看着，还是暂时离开（AFK）之后再回来看。

### 2. 把逻辑隔离进一个可移植模块

把真正的逻辑（回答问题的那一部分）放进单个 `<script>` 块，写成一个小的纯模块，日后可以被原样拎出、放进真实代码库。它周围的页面是一次性的；这个模块不是。

合适的形态取决于问题：

- **纯 reducer**：`(state, action) => state`。当动作是离散事件且状态是单值时合适。
- **状态机**：显式的状态与转换。当「当前哪些动作才是合法的」本身就是问题的一部分时合适。
- **一组小纯函数**，作用于一个朴素的数据类型。当不存在隐式的当前状态、只有转换时合适。
- **一个方法面清晰的类或模块**，当逻辑确实持有持续的内部状态时使用。

选择最契合所问问题的那种形态，而*不是*最容易接到页面上的那种。保持纯粹：没有 DOM，没有 `document`，没有伸进它内部的按钮处理器。页面调用它；没有东西反向流入。这正是让原型在其自身生命周期之外依然有用的关键：一旦问题得到解答，经过验证的 reducer/状态机/函数集就能独自迁移进真实模块。

### 3. 构建可分享的 HTML 文件

一个文件，朴素的 HTML/CSS/JS：没有框架，没有打包器，没有服务器，一切内联，双击即开，经得起邮件传来传去。任何人都应该能通过打开它来运行它。

为非开发者而写。每个标签都用**领域语言**，而不是代码语言：按钮和状态读起来像业务，而不是 reducer。用平实的文字解释正在发生什么。

用清晰的层级自上而下布局：

1. **标题与一句话说明**，道明这份演示让你探索什么（第 1 步的问题）。
2. **当前状态**：完整的相关状态，渲染成一个可读的面板（带标签的字段，而不是原始 JSON 堆砌），每次点击后重新渲染，让变化可见。在有助于非开发者跟随的地方，突出显示刚刚改变了什么。
3. **自由把玩按钮**：每个动作一个按钮，始终可用，任何人都能以任意顺序戳弄这个模型。每次点击派发对应动作并重新渲染状态。
4. **引导式走查**：一组**场景**，每个标签页一个。每个标签页先是一段简短的白话场景描述（它设定的情境和要留意的看点），其下方是该场景按顺序排列的**要按的按钮**。每一步都是一个真实按钮：点击它执行该动作并进入下一步。开始一次走查会重置到已知的初始状态，保证场景每次都以相同方式运行。

选择能展示棘手情形的场景——那些在纸面上难以推理的：正常路径（happy path）、刁钻的边界情况、一次对本应非法的操作的尝试。

保持美而有度：干净的排版、大方的间距、一个强调色。没有动画，没有花招：不让任何东西与状态和按钮抢注意力。

### 4. 交付

把文件发给他们，或替他们打开。他们有空时自然会点完走查、玩玩自由把玩；有趣的时刻是他们说「等等，这不应该是可能的」或「咦，我以为 X 会不一样」——那些是_想法_里的 bug，而这正是全部意义所在。如果他们想要新动作或新场景，就加上。原型会演化。

### 5. 记录答案与原型

一旦原型回答了它的问题，就记录答案，然后按 [SKILL](SKILL.md) 描述的方式记录原型。针对逻辑的具体映射：经过验证的 reducer/状态机/函数集迁移进真实模块（决策就此吸收）；HTML 外壳随一次性分支一起保留——该分支把原型作为一手来源——而且作为单个自包含文件，它在那里随时可以重新运行。

## 反模式

- **不要加测试。**需要测试的原型就不再是原型了。
- **不要接到真实数据库。**除非问题恰恰关于持久化，否则使用内存状态。
- **不要泛化。**不搞「万一以后想支持 X 呢」。原型只回答一个问题。
- **不要把逻辑和页面搅在一起。**如果纯模块引用了 DOM、`document` 或按钮处理器，它就不再可迁移。让页面保持为纯模块之上的一层薄壳。
- **不要动用框架、打包器或服务器。**一个收件人双击即开的文件；React 应用或开发服务器会毁掉「可分享」。
- **不要把 HTML 外壳发进生产环境。**页面是为手工点按优化的。它背后的逻辑模块才是值得保留的部分。
