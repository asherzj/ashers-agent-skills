一个松散的想法到来了：它大到单个 agent 会话装不下，还笼罩在迷雾中，从这里通往**目的地（destination）**的路还看不见。探路（wayfinding）要找的是这条路，而不是直冲目的地。本 skill 把这条路绘制成仓库工单系统（issue tracker）上的一张**共享地图（shared map）**，然后逐一推进其中的**决策工单（decision ticket）**（这些问题各自的解答本身就是一个决策，而不是待执行的构建切片），直到路线清晰为止。

目的地因每项工作而异，为它命名是绘图的第一步：它塑造之后的每一张工单。它可以是一份用于交接和迭代的 spec（规格说明）、一个在规划开始前就要锁定的决策，也可以是一次就地完成的变更，比如数据结构迁移。这张地图与领域无关：工程工作、课程内容，任何符合这个形状的东西都可以。

## 规划，而非执行

Wayfinder 默认做的是**规划**：每张工单解决一个决策；当路径已清晰、在有人去实际动手之前再无待决事项时，地图就算完成。那种想直接把活干了的冲动，通常正说明你已到达地图的边缘，该交接了。一项工作可以在其 **Notes** 中覆盖这一默认，把执行也纳入地图本身；但若没有这类说明，就产出决策，而不是交付物。

## 用名称引用

每张地图和每张工单都是一个 issue，因此都有一个**名字**：它的标题。在人类阅读的一切内容里（叙述文字、地图的 Decisions so far），都用这个名字称呼它，绝不用裸的 id、编号或 slug。满屏的 `#42, #43, #44` 无法辨读；名字一眼即懂。id 和 URL 并不会消失：名字包裹着它的链接，它们_藏在_名字里面，绝不能取而代之。

## 地图

地图是本仓库工单系统上的单个 issue，带 `wayfinder:map` 标签，是权威工件。它的工单是地图的子 issue。

地图是**索引**，不是存储。它列出已做出的决策，并指向承载细节的工单；一个决策只存在于一个地方——它的工单——所以地图从不复述决策，只给出摘要和链接。

**地图、其子工单、阻塞关系以及前沿（frontier）查询实际存放在哪里，因工单系统而异。** 工单系统本应已经提供给你。如果没有，请让用户运行 `/setup-matt-pocock-skills`。请查阅工单系统文档中的 "Wayfinding operations" 一节，了解_本_仓库如何表达这些内容。如果确实没有提供任何工单系统，默认使用 local-markdown 工单系统。

### 地图正文

整张地图的低分辨率视图，每个会话加载一次。open 状态的工单**不**列出：它们是 open 的子 issue，靠查询获取。

```markdown
## Destination

<what reaching the end of this map looks like: the spec, decision, or change this effort is finding its way to. One or two lines; every session orients to it before choosing a ticket.>

## Notes

<domain; skills every session should consult; standing preferences for this effort>

## Decisions so far

<!-- the index: one line per closed ticket, enough to judge relevance, then zoom the link for the detail the ticket holds -->

- [<closed ticket title>](link): <one-line gist of the answer>

## Not yet specified

<!-- see "Fog of war": in-scope fog you can't ticket yet; graduates as the frontier advances -->

## Out of scope

<!-- see "Out of scope": work ruled beyond the destination; closed, never graduates -->
```

### 工单

每张工单都是地图的**子 issue**；工单系统的 issue id 就是它的身份标识。工单正文就是问题本身，规模以一个 100K token 的 agent 会话为限：

```markdown
## Question

<the decision or investigation this ticket resolves>
```

每张工单都带一个 `wayfinder:<type>` 标签，取值为 `research`、`prototype`、`grilling`、`task` 之一（见[工单类型](#ticket-types)）。

会话通过把工单分配给驱动这张地图的开发者来**认领**它，而且要**最先**做、先于任何工作，这样并发会话就会跳过它。被分配人本身_就是_认领标记：一张 open 且未分配的工单即未被认领。

阻塞使用工单系统**原生**的依赖关系：这一点至关重要，因为它会在工单系统自己的 UI 里_可视化地_呈现前沿，让人不开地图就能看到哪些工单可以着手。只有缺乏原生阻塞的工单系统才退回正文约定。当阻塞某张工单的所有工单都已关闭时，它即**解除阻塞**；**前沿**是那些 open、已解除阻塞、未被认领的子工单，是已知区域的边缘。

答案不属于工单正文；它在解决时记录（见[推进地图](#work-through-the-map)）。解决工单过程中产出的资产从 issue 链接过去，而不是粘贴进来。

## 工单类型

每张工单要么是 **HITL**（human in the loop，需要_与_一位亲自为自己发声的人类共同推进），要么是 **AFK**，由 agent 独自驱动。HITL 工单只能通过这种实时交流来解决；agent 绝不代演人类那一方（一个自问自答的拷问 agent 就违反了这一点）。

- **Research**（AFK）：阅读文档、第三方 API 或知识库之类的本地资源，把某个决策正等着的事实挖出来。由一个以 "research" 调用 Skill 工具的子 agent 解决。当需要当前工作目录之外的知识时使用。
- **Prototype**（HITL）：以 "prototype" 调用 Skill 工具，制作一个廉价、粗糙、可供评判的具体产物（大纲、粗稿、stub 或 UI/逻辑代码）来提高讨论的保真度。把原型作为资产链接。当关键问题是"它该长什么样"或"它该有怎样的行为"时使用。
- **Grilling**（HITL）：对话。默认类型。始终以 "grilling" 和 "domain-modeling" 调用 Skill 工具两次。
- **Task**（HITL 或 AFK）：必须在做出_决策_之前完成的动手工作：没有可决定、可原型、可调研的内容，但在它完成之前讨论一直被阻塞。注册某个服务以便评判其 API、开通权限、搬运数据以看清其形状。这是唯一一种_做事_而非决策的类型，它靠为一个决策解除阻塞来赢得位置，而不是靠交付目的地。agent 能独自推进就独自推进（AFK）；否则给人类一份精确的清单（HITL）。工作完成即告解决；答案记录做了什么，以及后续工单所依赖的由此产生的事实（凭据位置、新 URL、行数）。

## 战争迷雾

地图_刻意_保持不完整：不要绘制你还看不见的东西。在现有工单之外是**战争迷雾**：对那些你确知会来、却还无法钉死的决策与调研的模糊视野，因为它们悬在仍然 open 的问题上。解决一张工单会清空它前方的迷雾，把如今已可明确表述的内容逐张升级为新工单，直到通往目的地的路清晰、不再剩下任何工单。

地图的 **Not yet specified** 一节写下的就是这份模糊视野：疑似的问题、稍后要重访的区域。它是_朝向_目的地的未发现前沿：这里的一切都在范围之内，只是还没锐利到能开成工单。视野允许写多略就写多略、能写多详就写多详；它还兼作路标，让协作者读出这项工作的去向。

**迷雾还是工单？** 判据是你现在能否把问题陈述得足够精确，而_不是_你现在能否回答它。

- 问题已经锐利时**开成工单**，哪怕它被阻塞、暂时无法行动。
- 还无法把问题表述得那么锐利时，写进 **Not yet specified**。不要预先把迷雾切成工单大小的碎块：它比一张工单更粗，一片迷雾等前沿抵达后可能升级成好几张工单，也可能一张都没有。

**Not yet specified** 不包含已经决定的内容（Decisions so far）、已是现有工单的内容，以及超出范围的内容（下一节）。

## 超出范围

迷雾只会_朝_目的地聚拢。目的地划定范围，因此范围之外的工作即**超出范围**：它不是迷雾，不属于 **Not yet specified**。它在地图上有专属的 **Out of scope** 一节：那些你已经有意识排除在_这项_工作之外的事。让一件事落到这里的是范围，而非锐利度。

超出范围的工作永远不会升级（前沿止步于目的地），所以只有目的地被重新划定它才会回来，而且是以一项全新的工作、而非一次续接的方式回来。

把某件事划为超出范围是一次划定边界的动作，不是路线上的一步。当一张已存在的工单被发现位于目的地之外（绘图时误纳入，或被某个解答暴露出来），**关闭它**（已关闭的工单明确不在前沿上），并在 **Out of scope** 一节留下一行：摘要加上它为何超出范围，并链接那张被关闭的工单。它不进 **Decisions so far**，那一节记录的是实际走过的路线；范围边界不是路线上的一步。

## 调用

两种模式。无论哪种，**每个会话解决工单绝不超过一张**，research 工单是唯一例外。

### 绘制地图

用户带着一个松散的想法调用。

1. **为目的地命名。** 以 "grilling" 和 "domain-modeling" 调用 Skill 工具两次，敲定这张地图探向何处：那份 spec、那个决策，或那次变更。目的地划定范围，所以最先定它。
2. **绘制前沿。** 再次拷问，这次**广度优先**：横向铺满整个空间，而不是在单条线上深挖，把未决决策和眼下就能迈出的第一步浮出来。**如果这一步没有浮出任何迷雾**（通往目的地的路已经清晰，整段旅程小到一个会话就能走完），你不需要地图。停下，询问用户想怎么继续。
3. **创建地图**（标签 `wayfinder:map`）：填好 Destination 与 Notes，Decisions so far 留空，把迷雾草绘进 **Not yet specified**。
4. **把现在就能明确表述的工单**创建为地图的子 issue，然后在**第二轮**里接上阻塞边（issue 必须先有 id 才能互相引用）。接线把它们分成前沿与被阻塞两类；你还无法明确表述的一切都留在迷雾里：**Not yet specified** 一节。
5. **放出 research 子 agent。** 为你刚创建的每张 `research` 工单派一个以 "research" 调用 Skill 工具的子 agent 并行解决，把发现捕获到一次性分支 `research/<name>` 上，并从工单留下指向它的上下文指针。
6. 停下：绘图是一个会话的工作；它不亲手解决任何工单。

### 推进地图

用户带着一张地图（URL 或编号）调用。工单是**可选的**：没有指定工单时，下一个决策由你来挑，而不是用户。

1. 加载**地图**：低分辨率视图，而非每张工单的正文。
2. 选工单。用户点了名就用那张。否则按顺序取第一张前沿工单。**认领它**：在任何工作之前先把它分配给你自己。
3. 解决它。**按需放大**：按需获取任何相关或已关闭工单的完整正文；`## Notes` 块点名了哪些 skill，就以它们调用 Skill 工具。拿不准时，以 "grilling" 和 "domain-modeling" 调用 Skill 工具两次。
4. 记录解决：把答案作为**解决评论**发出，**关闭**该 issue，并向地图的 Decisions so far **追加一条上下文指针**。
5. 补上新浮出的工单（先创建后接线）；把答案已使其可明确表述的迷雾升级掉，从 **Not yet specified** 清除每一片已升级的迷雾，让它只以新工单的形式存在。如果答案揭示某张工单（这张或别张）位于目的地之外，**把它划为超出范围**，而不是在路线上解决它。如果该决策使地图的其他部分失效，更新或删除那些工单。

用户可能并行推进已解除阻塞的工单，所以要预期其他会话正在并发编辑工单系统。
